# Design

## Context

现有实现把单张图片读入 `self.image`，由 `detector.py` 完成检测与标注，`app.py` 负责 Tkinter 预览和 PIL 导出。图片模式已经通过两张示例图验收，视频相关代码尚不存在。行为要求见 `specs/video-detection/spec.md`，动机见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 将视频读取与元数据封装为不依赖 Tkinter 的模块，可在无显示器环境测试。
- 图片与视频共用现有检测、参数、预览和导出路径，避免复制逻辑。
- 播放、暂停、单步和定位使用主线程定时器，先保证正确性和可维护性。

**Non-Goals:**

- 不导出整段标注视频，不处理音频。
- 不实现跨帧跟踪、平滑或目标 ID。
- 不接入实时相机，不做 GPU 加速或多视频并行。
- 不承诺所有编码器的帧精确 seek，定位精度按解码器能力记录。

## Decisions

- 新增 `hough_circle_gui/video.py`，用 `VideoSource` 包装 `cv2.VideoCapture`，提供打开、读取、定位、释放和元数据。理由：沿用 `detector.py` 与 UI 分离的既有模式；替代方案是直接在 `app.py` 操作 `VideoCapture`，难以做无显示器测试。
- 引入媒体模式（图片/视频），当前帧统一放在 `self.image`；`_run_detection`、`_render`、`export_annotated` 保持单入口。理由：图片行为不变，视频复用同一套标注与导出。
- 播放循环使用 `root.after`，每次读取并检测一帧；间隔取 `1000 / fps` 毫秒，帧率未知或无效时回退到 100 ms。不设上下限，避免低帧率视频被人为加速。检测慢于间隔时不丢帧、不排队，播放会慢于实时。理由：无锁、无队列、界面在帧间可响应；替代方案是解码线程加帧队列，复杂度更高，留到需要实时播放时再做。
- 参数变化沿用 150 ms 防抖：暂停时重检当前帧，播放时当前帧重检后继续；后续帧自动使用新参数。理由：与图片模式一致。
- 定位使用 `CAP_PROP_POS_FRAMES` 设置后读取一帧，以实际读到的帧为准；编码器只支持关键帧定位时允许近似。总帧数未知时禁用按总帧数的进度条，但保留上一帧/下一帧和播放。界面帧号从 1 开始，内部索引从 0 开始。理由：跨容器最简；替代方案是逐帧丢弃，长视频代价高。
- 元数据缺失时把帧率和总帧数显示为未知，仍允许逐帧播放。理由：部分编码器返回 0 或不可靠值。
- 读取结果区分“有帧 / 结尾 / 错误”：已知总帧数且位置到达末尾按结尾处理；打开后一帧都读不到按错误处理；未知总帧数时读到 `None` 按结尾处理并在状态栏说明。理由：OpenCV 对结尾和解码失败都返回 `False`，不能静默崩溃。
- 导出只保存当前标注帧，复用 PIL 保存路径，不引入视频编码依赖。导出前检查当前帧是否已按最新参数检测；若防抖尚未触发或刚完成定位，先同步重检当前帧再保存。理由：避免导出上一帧或旧参数的标注，同时符合非目标。

## Risks / Trade-offs

- 编码器兼容性取决于目标机器的 OpenCV/FFmpeg 构建 → 在 README 和验收记录中写明实测容器/编码器；失败时提示具体路径和解码错误，不崩溃。
- 逐帧 Hough 检测是 CPU 密集操作，1080p 可能明显慢于实时 → 播放不丢帧但会变慢；后续可加解码线程、抽帧或性能优化。
- 总帧数、FPS 和定位精度可能不可靠 → 显示未知、允许逐帧操作，并在验收中记录实际表现。
- 检测在主线程执行，单帧检测期间界面短暂停顿 → 沿用现有图片模式；大视频/高分辨率时应先测再决定线程化。
- 视频旋转元数据可能不被 OpenCV 自动应用 → 在已知限制中说明；需要时后续按 `CAP_PROP_ORIENTATION_META` 处理。
- 样例视频来源和体积 → 优先由现有两张验收图生成短片段，记录生成命令、大小与哈希；大文件不入库。

## Migration

无数据或接口迁移。图片模式保持现有行为；新增视频入口和 `video.py`。回滚时移除视频入口即可，不影响图片流程。
